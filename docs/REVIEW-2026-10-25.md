# HypGraph + hypswarm — end-to-end review, 2026-10-25

Scope: `hypgraph` (branch `harmony-study`, the engine the harmony study runs on) and `hypswarm` 0.1.0a1 (`main`).
Read in full: hypswarm's whole source (2,170 lines incl. tests); hypgraph's `stats`, `policy`, `server`, `coord`
(predicates, recipes, issue_work), `graph.create`, `checks.claim_issues`, and the MCP author binding. Not re-read
line by line: `derive.py`, `plan.py`, `bundle.py`, `report_check.py`, `cli.py` (covered by the 2026-10-24 review
and 91 passing tests). Baselines before any change: hypswarm 17 tests / 6.6 s; hypgraph 91 tests / 11.4 s.

The principle everything below is judged against: **models do the reasoning, the record holds the authority, and
no agent can skip the evidence its work is accepted on.**

## What holds

- The integrity kernel is still dependency-free and append-only; standing is derived on read, never set; every
  write is an event pinned by hash. Nothing in hypswarm reaches around it — workers only ever call the record's
  own `create` / `review` / `return_work`.
- Orchestration is deterministic: the scheduler makes no model calls, and every scheduler action is an event in
  the record (orders are task nodes, acceptance a decision). The run can be audited from the record alone.
- Acceptance is predicate-based (`run_registered`, `result_exists`, `claim_made`, `reviewed`, …), checked by the
  record against evidence written **after** the order was issued (lease-window evidence). A worker cannot return
  "done" by saying so.
- Claim checks refuse unbound numbers, absolutes without k/n, exclusions without power, hedged conventions; the
  refusal log keeps what was caught. Auto-binding repairs before refusing (D-8), negation is clause-level (D-7).
- Pilots 2–4 (so far): the record condition hits no traps, and the harness caught its own measurement hazards
  (provider stalls) and fixed them in the record (D-9, D-16).

## Findings, ranked by risk

| # | area | finding | severity |
|---|---|---|---|
| 1 | **budget enforcement under concurrency** (hypswarm `budget.py`, `worker.py`) | `Meter.check()` then `await model.complete()` then `Meter.add()`: with N workers in flight and one call left, all N pass the check and all N are billed. Overshoot is bounded by the number of parallel seats, but a *hard rule* that can be exceeded by 4 calls is not a hard rule. The dollar cap is checked only after money is spent. | **high** |
| 2 | **authentication boundary** (hypgraph `server.py`, `policy.py`; hypswarm `http_record.py`, `record.py`) | The record server authenticates nobody and takes `author` from the request body. Anyone who can reach `--writable` can write as any non-reserved author — including **`harness`**, which hypswarm treats as the orchestrator (owner of every order, may cancel and rework) but which `Policy.reserved` does not know. An external MCP worker could issue, cancel or settle orders. The MCP server fixes its author at start (`--as`), so that path is sound; HTTP is not. | **high** |
| 3 | **statistical correctness** (hypgraph `stats.py`, `checks.py`) | Formulas are right (rule-of-three at k∈{0,n}, Wilson otherwise, Newcombe hybrid-score interval, pooled two-proportion z). But `two_proportions` / `detectable` divide by zero at `n=0` (a claim with an empty arm would crash `create` instead of refusing it), and there is no test pinning the numbers to known values — a future "simplification" could drift them silently. | medium |
| 4 | **fault recovery** (hypswarm `run.py`, `scheduler.py`) | A crashed or killed run leaves open orders and leases in the record, and `run()` can only start a *new* investigation. The record has everything needed to resume (orders, assignees, rework chains, returns), but nothing reads it back. | medium |
| 5 | **capability-aware routing** (hypswarm `seats.py`, `scheduler.py`) | One model per seat for the whole run. A cheap model that fails an order's predicates is reworked on the same cheap model; the only deeper model is the lead, reached after two reworks. No way to say "escalate this seat's model when its first attempt comes back NOT MET". | medium |
| 6 | **trusted artifact execution** (hypswarm `tools.py`; study runners) | Files reach workers as bytes staged by the host; the record holds their hashes but nothing verifies the bytes a worker reads against the record before use, and a notice's corrected file is registered but not checked against what was delivered. Agent code runs in the study's sandboxed python tool (host-side); hypswarm itself ships no execution tool, which is right, but the contract "verify the hash before you trust the file" is not stated or enforced anywhere. | medium |
| 7 | **governance profiles** (hypgraph `coord.py` DEFAULT_DONE, `checks.py`) | Acceptance predicates and claim checks are one fixed set tuned for the scientific case (claims, reviews, k/n). An engineering task (a requirement, a passing test) or an optimization task (an objective value under constraints) has no vocabulary for "done" beyond `result_exists`, and no way to version the rules an investigation was run under. | medium (extension, blocking the "general-purpose" goal) |
| 8 | per-order budget vs lead | `per_order_calls` counts the lead's exception turns under `"<code>:lead"`, a different unit from the order itself, so an order's own cap doesn't include its exception handling. Documented behaviour, but worth knowing when reading costs. | low |
| 9 | `HttpRecord._raise` maps every 4xx but 404 to `GraphError` | A 401/403 from an auth layer reads as a record refusal. Fine until finding 2 is fixed; then the auth error should be its own exception. | low |
| 10 | `Scheduler._assign` issues reviews for `answered` questions only when reviewers exist; with none, questions never settle | By design (a question settles on one checked claim) — but the run then ends `stuck` with every answer in the record. Should be surfaced as "no reviewer seat: questions can be answered but never settled" at `run()` time. | low |

## What this review does not find

- No path by which a worker writes an acceptance, a review of its own work, or a lab-recorded run (`kind=lab`
  needs the instrument; `accept_work` is the harness's; `review` refuses the author's own nodes).
- No scheduler decision that depends on model output.
- No place where the record's refusals can be bypassed by phrasing: the checks run in `create`, not in a tool.

## Plan (incremental, each step tested and benchmarked against the baseline above)

1. Budget: reservations (`Meter.reserve` / `release`; `add` consumes) so the check counts calls in flight;
   dollar reservation by the running average cost per call. Test: five parallel workers, three calls → exactly three.
2. Auth: `hypgraph serve --writable --token <secret>[=<author>]`; a bound token may write only as its author, an
   unbound one as any non-reserved author; `Policy.extra_reserved` so hosts can reserve names such as `harness`;
   `HttpRecord(token=…)` and a distinct `AuthError`. Default (no token) unchanged on localhost.
3. Stats: guards for empty arms (refuse, don't crash); a known-values test (Wilson 3/10 = 0.108–0.603, rule of
   three, 10/100 vs 20/100 p ≈ 0.048).
4. Resume: `run(..., resume=<inv>)` adopts open orders from the record, redispatches to their seats, keeps rework
   counts from the chain. Test: stop after the first dispatch, resume on the same file, settle.
5. Escalation: `Seat.escalate_to` (a model id) used from the first rework onward; recorded on the order. Test:
   cheap stub fails the predicates, deep stub passes on the rework.
6. Profiles: `hypgraph.profiles` — versioned sets of default predicates per target type, completion criteria for
   an investigation, and extra domain validators (`scientific@1`, `engineering@1`, `optimization@1`); pinned on
   the investigation; no profile → today's behaviour exactly.
7. Artifact trust: a worker-side `read_file` that returns bytes only when they hash to a live artifact in the
   record (the study runners keep their own sandbox); a notice's files are registered before they are delivered.
8. Benchmark: the stub task on the pre-change commit and after each step — tests, wall time, scheduler rounds,
   model calls; no real model spend.

Every step has an ADR in `docs/decisions/` (hypswarm) or `docs/decisions/` (hypgraph) with the decision, the
alternatives, and the measurement.

## Progress (same night)

Done, each with tests and an ADR: **1** budget reservations (ADR-001; 7 calls against a cap of 3 → exactly 3);
**2** token-bound writes + `Policy.extra_reserved` + `AuthError` (HypGraph ADR-001, hypswarm ADR-002); **3** stats
guards and known-value tests; **4** `run(..., resume=)` (ADR-003) — which found that `cancel_work` left the target
leased, fixed in the engine; **5** `Seat.escalate_to` on the record's NOT MET (ADR-004); plus an `on_request`
capture hook on the OpenAI-compatible provider. Pilot 4 (same night) added two findings:

| # | area | finding | status |
|---|---|---|---|
| 11 | **roles the scheduler must hold** (`tools.py`, `scheduler.py`) | The only reviewer seat wrote the claim answering a question; the scheduler excludes a claim's author from its reviewers, so the question could never settle and both F7 hypswarm runs ended `stuck` with no report, the lead having spent its report turns planning. | **fixed** — ADR-005: reviewer seats can't write claims; an unreviewable answer is re-issued once to a worker; the report phase has reading and submitting tools only |
| 12 | lease-window rule resolution (`coord._after`) | "Only evidence written after the order counts" compares ISO timestamps at one-second resolution: a claim written in the same second as the order counts for it. Harmless in real runs (seconds apart), visible in tests. Event sequence numbers would be exact. | open (HypGraph) |

Not done: **6** artifact-hash verification before a worker reads a file; **7** governance profiles (design in the
plan above; it is the extension and should not be rushed in the same night as the hardening); the F7 record-run stall is
**diagnosed**: replaying the captured request through the proxy, the exact request (system message + 8 tool schemas)
times out every time, any 7-tool subset or a one-character change to the *system* message answers in ~1 s, and a
change to the user message or to max_tokens still hangs — a provider-side cached-prefix entry that never returns.
Not a bug in either codebase; mitigation is a per-run first line on every system prompt (study D-17).

**Benchmark (no spend).** `bench/stub_bench.py`, the alpha task 20× on scripted models, in-memory record, on the commit before tonight (03ff9b2) and after ADR-001…005: identical — 20/20 settled, 12 model calls per run (min = max), 4 scheduler rounds, 4 orders, 0 reworks, median 15 ms a run. The hardening changed no decision the scheduler makes when every seat does its job; what it changed is what happens when one doesn't.
