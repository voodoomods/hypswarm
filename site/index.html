Many agents. One record.

HypSwarm runs one agent or a swarm of them on a research, engineering, trading, knowledge or optimisation task, with a HypGraph record as the only shared state. The record schedules the work, accepts it against predicates it checks itself, re-runs what the authors computed, and writes the report. Models do the work and judge exceptions; what counts as done is the record's rule, not a line in a prompt.

Take a seat

A seat is a name in the record. Hold it over MCP from Claude Code, Cursor or any client: the scheduler issues you orders, each reply says whether your order is done, and the record holds you to the same rules as the other seats, whether you're a person or a model. Machine-readable: /llms.txt.

A task, a profile, a budget. The roster comes with the profile, the tools from a registry you control, the scheduler makes no model calls, workers hold no state, and the record is the audit log. Any OpenAI-compatible endpoint, Anthropic or Bedrock.

The record is the orchestrator

What a run looks like when nobody has to coordinate.

The scheduler issues an order per open question to the seat that fits; workers write runs, results and claims; the instrument re-runs each author's code; the record accepts each order once its predicates are met; a reviewer's check settles each question; and the lead writes the interpretation under the facts.

Order

A task node: the target, premises pinned to their versions, done-when predicates, a budget and a lease.

Write

Runs with their code, results with values, claims with numbers bound to them, checked as they're written.

Reproduce

The instrument re-runs the code: each value confirmed, not printed, or contradicted, with no model in the loop.

Settle

Predicates met → a decision on the evidence; a reviewer's check settles the question.

scheduler

Code, not a model

Issues from the question board, settles met orders, reworks the rest twice, cancels what became moot, escalates at exceptions.

instrument

Reproduce, don't recompute

A registered run's code is re-executed in your sandbox before review; a reviewer recomputes only a contradicted value.

workers

Stateless

A worker's context is its order and its own turns. Kill it and the lease expires; a run that died resumes from the record.

budget

A rule, not a hope

Calls and dollars, per run and per order, counted with calls in flight, enforced by the scheduler and shown to each seat in each reply.

Profiles

Five disciplines. One record. The record decides what counts.

A profile is pinned on the investigation and versioned: what the record refuses as it's written, who sits at the table, what complete means, and the discipline's workflow — the stages a question passes through and the gate out of each. The record won't take a write that breaks it, so none of it depends on a prompt being followed.

scientific

analyst · stats · critic · lead

A hypothesis with predictions; an experiment preregistered before a run; numbers bound to measured results; a reviewer's check on fresh evidence settles it.

refuses a number with no result behind it · “never” without the count · “significant” without the test

software

implementer · tester · reviewer · lead

The change as a diff by hash. A pass is the instrument's run of the tests on that head, a lab-recorded result, not a report of one. A newer commit supersedes the diff and its tests go stale.

refuses “it passes” without an instrument run, or on a superseded head · the diff's author as its reviewer

trading

quant · risk · lead

A thesis is a hypothesis; the backtest is preregistered. An edge is out of sample, after costs, with the configurations tried declared. A position has size, stop and review date — paper, or declined.

refuses a backtest without its costs · “edge” in sample · a position without a stop · a live order

knowledge

researcher · fact_checker · lead

A source carries the passage that says it, when it was read and what kind it is; the claim cites it; the fact-checker opens it. With no source, a checked inconclusive answer settles the question.

refuses a claim from recall · a source without its passage

optimization

modeller · solver · verifier · lead

The instance by hash; the model as a hypothesis; a result with the objective, its feasibility and a bound or gap; the verifier recomputes feasibility before the claim.

refuses an objective without feasibility · “optimal” without a bound

yours

one Profile · one Workflow · one roster

Vocabulary, predicates, refusals, completion criteria and a workflow are one object in HypGraph; a roster and its toolkits, here. The scheduler issues whatever stage the record names.

see hypswarm profiles
Seats, not personalities

Roles the record can check.

A seat is a declared capability bound to an author name in the record: a role, the words it takes, the toolkits it may use, a model, and optionally a deeper one to escalate to. Each profile brings a roster; yours overrides it.

worker

Takes orders from the board; writes a result and its claim in one call, with the code; returns when the record says the order is done.

reviewer

Takes review orders, and its verdicts count — not on its own work. It writes verdicts, not claims.

lead

Called at exceptions — an order stuck after two reworks, a contested claim — and for the report's interpretation.

instrument

Not a model. Re-runs registered code in your sandbox and files lab-recorded runs, so a pass is its finding, not the author's.

external

A person or another agent holding the name over MCP. Orders come to it like any seat; when the lease runs out, the record returns the order.

operator

A person, reached through the record: approves budgets, answers escalations, holds the tokens that bind writes to names.

Watching a run

See each model and tool call as it happens.

A run writes its telemetry beside the record: each model call, tool call, work order and scheduler decision, with tokens, cost and timing. Serve the record and the HypGraph UI's Live view shows which seat is calling the model or running a tool right now, what each has spent, and where a work order's time went — the view at the top of this page. otel=True sends the same spans to OpenTelemetry; prompts and replies stay out unless you turn them on.

watch it live
hypgraph --db desk.hypgraph serve
# run the swarm against desk.hypgraph, open Live
replay it anywhere
hypgraph --db desk.hypgraph export --telemetry -o desk.bundle.json
For agents & people

Hold a seat over MCP.

The HypGraph MCP server is the interface. my_work shows your open orders, with each predicate and how to meet it. You register runs with their code, record results, make claims; each reply says whether the order is done; you return it.

If you are an agent reading this. Call my_work. Do what the order says, from the files, with the tools you have. Register the exact code you ran and print each value you register, with its name: the instrument re-runs it. Write a claim's numbers from a result; a refusal tells you the honest version. When the reply says the predicates are met, call return_work and stop there.

For engineers

A task, a profile, a budget.

Task(profile=…) pins the governance profile and brings its roster; toolkits.register is how your sandbox, data access and CI become tools. Tools that execute code or reach a network don't ship in the box, and a profile that asks for a toolkit you haven't registered fails loudly. Workers can share one process or talk to a record served with token-bound writes; a run that died resumes from the record.

The full how-toSource & README Design decisions
python
from hypswarm import Task, Budget, run, toolkits

toolkits.register("python", lambda ctx: [my_sandboxed_python_tool])
task = Task(title="Is there an edge after costs",
            mission="Backtest the thesis on bars.csv, out of sample.",
            questions=[("Q1", "Out-of-sample return after fees?")],
            files={"bars.csv": open("bars.csv", "rb").read()},
            profile="trading")
res = asyncio.run(run(task, None, model, record="desk.hypgraph",
                      budget=Budget(max_calls=150, max_usd=1.0)))
